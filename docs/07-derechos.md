# Derechos, privacidad y publicación

Análisis inicial de producto del 5 de septiembre de 2026. Hipótesis de trabajo: responsable establecido en España y primer mercado en España, pendientes de confirmación. La disponibilidad en otros países necesita evaluación territorial. Este documento prepara decisiones y revisión jurídica; no acredita licencias obtenidas.

## Aplicación del enfoque del hilo

El [hilo de referencia](https://chatgpt.com/share/6a9c3582-0188-83eb-856c-772781f3a065) distingue catalogar/enlazar, integrar servicios externos y alojar con autorización. Stunafy conserva esas tres vías y evalúa sus condiciones por separado. Tener permiso de un titular musical no elimina las restricciones del servicio usado para acceder a su archivo.

El enriquecimiento mantiene licencias y atribuciones por material. Un archivo recibido por dos vías no hereda el permiso más amplio sin comprobar que cubre esa edición y el canal de acceso. El contexto histórico se redactará con fuentes, sin copiar artículos completos. Referencias a publicaciones de pago podrán dirigir al proveedor sin incorporar su contenido protegido.

No se ha encontrado en el hilo una autorización de titulares ni un análisis jurídico individualizado. Su valoración de abundancia o acceso gratuito sirve para investigar, no para habilitar importación o publicación.

## Capas de derechos

La legislación española distingue derechos sobre obras, transformaciones, interpretaciones, fonogramas y bases de datos. Reproducción, distribución, comunicación pública y transformación tienen alcance propio. Las duraciones y reglas transitorias impiden asumir que toda canción antigua o tradicional es de dominio público. La protección de un arreglo o grabación se examina además de la composición. Referencia: [Ley de Propiedad Intelectual, artículos 11, 17–21, 26 y siguientes, 105 y siguientes, 133 y siguientes y disposiciones transitorias](https://www.boe.es/buscar/act.php?id=BOE-A-1996-8930).

## Política de Stunafy propuesta

| Contenido/uso | Evidencia que se pedirá antes de habilitarlo |
|---|---|
| Metadatos | Origen, condiciones de reutilización y evaluación de extracción del conjunto |
| Audio | Alcance sobre composición/letra, interpretación y grabación; streaming, territorio y vigencia |
| Letra | Autorización o base documentada para mostrar el texto y sus variantes/traducciones |
| Acordes | Procedencia de transcripción, condiciones y alcance de adaptación/transposición cuando corresponda |
| PDF/partes | Composición, arreglo, transcripción/edición y permiso de exhibición, descarga o impresión según acción |
| MIDI/MuseScore | Derechos del contenido musical y archivo; uso, reproducción o modificación expresamente evaluados |
| Portadas, fotos y escudos | Permiso de imagen/obra y uso de marca cuando proceda |
| Offline | Autorización de copia local con periodo, dispositivo, territorio y condiciones de retirada |

Una URL pública, la atribución o que un archivo se pueda descargar no acreditan permiso para redistribuirlo. La etiqueta «popular» se trata como un dato de la fuente, no como dictamen sobre dominio público. La posesión de una copia o una autorización de la agrupación puede no cubrir todos los titulares necesarios.

Para material con licencia abierta, registrar nombre, versión, URL y evidencia de que quien licencia puede hacerlo. Revisar restricciones comerciales, obras derivadas, atribución y compatibilidad con transposición y distribución. No generalizar una licencia de una página a todos sus adjuntos.

## Acciones y decisiones de permiso

Acciones internas: mostrar metadatos, mostrar texto, reproducir audio, mostrar partitura, transformar, imprimir, descargar, guardar offline y mostrar contenido externo. Cada una tiene decisión independiente: pendiente, permitida, denegada, caducada o revocada.

El registro incluye recurso y revisión, titulares/capas cubiertas, territorios, inicio/fin, permiso comercial, atribución, evidencia privada, responsable y próxima revisión. La publicación requiere cubrir conjuntamente todas las capas necesarias. No basta con encontrar un permiso aislado si otro derecho sigue pendiente.

El valor inicial es pendiente. «Dominio público verificado» registra razonamiento, territorio y evidencia; tampoco autoriza automáticamente una edición o grabación moderna.

## Plataformas externas

**YouTube.** Sus políticas de API restringen descargar o almacenar contenido audiovisual, el acceso offline, separar audio y la reproducción de fondo. También regulan agregación y conservación de datos. Propuesta: enlaces externos en la primera versión; un reproductor oficial futuro requiere revisar el flujo completo, atribución, privacidad y política vigente. No extraer audio para el reproductor de Stunafy. Fuente: [políticas de YouTube](https://developers.google.com/youtube/terms/developer-policies).

**Spotify.** Su política limita streaming a usuarios Premium, restringe usos comerciales de aplicaciones de streaming y prohíbe determinados servicios integrados con streams o contenido de otros servicios. Por ello, no se propone una cola que combine Spotify con el catálogo propio. Incluso una integración de metadatos requiere revisar condiciones, atribución, acceso y conservación. Fuente: [Spotify Developer Policy](https://developer.spotify.com/policy).

La sugerencia del hilo de descubrir automáticamente nuevas tunas por artistas similares necesita corregirse como dependencia técnica: Spotify anunció restricciones de acceso a Related Artists para nuevos casos de uso. Stunafy no contará con ese endpoint sin comprobar elegibilidad actual. La navegación manual en Spotify y el acceso de una API son capacidades distintas. Fuente: [cambios de Web API publicados por Spotify](https://developer.spotify.com/blog/2024-11-27-changes-to-the-web-api).

**SoundCloud.** Las condiciones de API prohíben almacenamiento persistente y acceso offline de contenido de usuarios; la caché temporal está limitada a la sesión. La posibilidad de descargar en SoundCloud no habilita esa función mediante su API. Un permiso directo del titular para recibir archivos por otro canal se evaluaría como una vía independiente, sin eludir las condiciones de la plataforma. Fuente: [API Terms of Use](https://developers.soundcloud.com/docs/api/terms-of-use).

No se han comprobado credenciales, cuotas ni elegibilidad de acceso de Stunafy a estas APIs. Su viabilidad no forma parte de lo confirmado.

## Aportaciones, reclamaciones y retirada

Primera fase con aportaciones editoriales privadas. Solicitar identidad, relación con titulares, usos concedidos y documentos de respaldo. La aceptación de términos por un colaborador no sustituye verificar sus facultades cuando existan dudas.

Publicar un canal de reclamación; registrar recurso, reclamante, motivo y evidencias; suspender preventivamente el acceso afectado cuando corresponda; revisar y documentar la resolución. Propagar las retiradas a derivados y cachés. Conservar pruebas restringidas solo durante el periodo justificado.

Antes de aportaciones públicas o comentarios, evaluar las obligaciones de intermediación/moderación aplicables al servicio y los mecanismos de denuncia. No se presupone que la primera configuración cubra una futura red social musical.

## Datos personales

Diseño propuesto: cuenta con datos mínimos; historial opcional, privado y borrable; playlists privadas por defecto; representante de agrupación con verificación separada. Evitar recopilar direcciones, ubicación precisa o contactos personales sin necesidad funcional.

Definir responsable, finalidades, bases jurídicas, plazos, encargados, transferencias y atención de derechos antes del lanzamiento. Evaluar cookies, analítica y reproductores externos antes de incorporarlos. Usar la norma aplicable como referencia y no pedir consentimiento indistinto para todo tratamiento. Referencia: [RGPD, texto oficial](https://eur-lex.europa.eu/eli/reg/2016/679/oj?locale=es).

Propuesta inicial de retención para revisar: historial hasta borrado del usuario o 12 meses; registros operativos 30 días; evidencia de derechos según contrato y obligaciones aplicables. Estos plazos son decisiones pendientes, no exigencias legales universales. Backups y eliminación deben tener un calendario documentado.

## Preparación para Google Play

La distribución Android contemplará APK firmado para pruebas/distribución directa y Android App Bundle para Google Play. Se comprobará el nivel objetivo de API exigido en la fecha de entrega. Fuente: [crear y configurar una aplicación](https://support.google.com/googleplay/android-developer/answer/9859152).

Con creación de cuentas, preparar eliminación accesible dentro de la app y el recurso web requerido, junto con tratamiento de datos asociados y excepciones justificadas. Documentar privacidad y prácticas de SDKs. Fuente: [política de datos de usuario de Google Play](https://support.google.com/googleplay/android-developer/answer/10144311).

Lista de entrega propuesta: titular y cuenta de desarrollador verificados, permisos musicales archivados, nombre/marca revisados, política de privacidad pública, declaración de datos coherente con SDKs reales, clasificación de contenido, permisos Android mínimos, pruebas en dispositivos y credenciales de revisión si se requieren. Confirmar requisitos de pruebas de la cuenta concreta y políticas vigentes antes de enviar.

La publicación y el modelo de pago no están aprobados todavía. Si se incorporan suscripciones o ventas digitales, se revisarán las condiciones de tienda y contratos de contenido para ese modelo.
